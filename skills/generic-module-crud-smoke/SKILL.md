## External Dynamic Collection Contract

- Keep application-independent dynamic collection rules in `data/dynamic_collections.json`; do not add field-name branches to `module_driver.py` and do not require production frontend markup changes for a test-only contract.
- Match one rule by its exact `formCode` and normalized `component` path. A rule must declare a collection root, row creation selector, row selector, `minRows`, and child fields whose `fieldCodeTemplate` contains `{index}`.
- First fill only the ordinary top-level fields that can reveal a conditional collection root. Then create the minimum configured rows and fill every declared child through `FieldInteractor` scoped to that row. Ordinary DOM scanning must skip every control inside a manifest-owned root, so a generated `el-id-*` control cannot overwrite a typed dynamic value. Submit and read back child array paths such as `items.0.description`; exclude only the UI wrapper collection code such as `riskItems` from comparable readback.
- Missing root, unavailable row creation, absent child control, or an unsuccessful child fill is a `DynamicFieldContractError`. Report it as a contract/configuration failure, never as a product save or delete failure.
- Every CommonFieldExecutor entry point, including Batch and independent common-field validation, loads the same matching dynamic-collection specs as module smoke using the current `formCode` and component. Do not let one execution path silently omit a collection contract that another path applies.
- Configure and click the visible collection component wrapper (for example an Element Plus `.el-checkbox` label), never a clipped internal native checkbox/radio input. Normalize activation failure to `DynamicFieldContractError` so Batch stops once with a shared-precondition diagnosis instead of amplifying it into later field failures.
- For Element Plus selects, prefer the control-owned popper from `aria-controls`, but treat an absent or hidden owned popper as stale after rerender. Fall back only to a visible select/cascader popper that contains enabled option nodes; do not scan generic tooltips or messages. Cover both the stale-owned-popper recovery and the ordinary owned-popper path with Playwright-shaped `.last` locators.
- Emit `COMMON_TRANSACTION_FAILURE` with the transaction ID and sanitized exception before converting an ordinary transaction exception to logical `execution_failed` results. This keeps a live batch diagnosable without waiting for the final aggregate assertion.
- Treat an observed backend `HTTP 401` during shared baseline work, including required attachment upload, as a browser-authentication shared precondition. Stop opening later transaction forms and mark their logical rows blocked; do not relabel expired login state as missing select options, field validation, or product defects.
- Detail-module action lookup retains its normal rendering wait while the target has no stable visible content or still shows a loading indicator. Once visible target content has remained unchanged through the configured grace window and the requested action is still absent, stop immediately with the existing missing-action contract failure; do not repeat the full action timeout for every candidate parent record. Do not preflight configured dynamic-collection roots before conditional baseline fields have had a chance to reveal them.
- Vue component props such as `<el-form-item :prop="...">` are source contracts, not guaranteed rendered DOM attributes. For an editable table without test attributes, bind each child to an exact rendered column header plus a column-scoped control selector, derive the current cell from the table header/class relationship, and keep `fieldCodeTemplate` only as the stable payload/readback identity. Missing or ambiguous headers, duplicate controls, and unexpected editable controls must raise `DynamicFieldContractError` before save.
- Treat `minRows` as the minimum creation threshold, not the number of rows to validate. A selected business entity may hydrate many existing collection rows; inspect every rendered editable row, preserve every non-empty child value, and fill only empty declared children before Save. Keep the final all-row control/value check so a partially hydrated row cannot reach the backend as an invalid collection payload.
- Once a collection root is uniquely scoped by its exact section title, locate row creation through that section's stable toolbar and rendered button class. Do not add an unverified direct-child or exact-text pseudo-selector on top of the unique root; framework button wrappers can make the visible command fail that redundant selector. Keep the configuration regression exact and let runtime visibility/actionability checks reject an absent or disabled command.
- Nested add/delete actions must resolve the nearest independently titled table section (for example `.enterprise-section`) and use only that section's button and rows. Do not use a shared dialog ancestor or `first`/`last` as a cross-section fallback; a nested delete creates and removes only its own temporary row while retaining the legal baseline row.
- A manifest-owned nested row filled by `_fill_configured_collection_row` has its own failure boundary. Its completion check may combine only that row's fill failures and current empty required controls; never reuse `_fill_failures` left by the parent form or a previous generic row. Parent failures remain parent-form evidence and must be reported at the parent completion gate rather than mislabeled as the nested action.
- Declare a collection-local numeric dependency in `valueRelations` only when both endpoints are declared numeric children of the same exact `formCode`/component collection. Enforce the relation after the whole row is filled and before Save; `adjustOrder` may change only values generated in that row. Preserve hydrated/page values and Excel target mutations, and raise `DynamicFieldContractError` when a violated relation has no safe generated endpoint instead of silently rewriting business data.
- A declared collection can remain available for an explicitly selected nested action without being a valid outer-Add baseline. Validate collection contracts by the active lifecycle: parent filling checks only `createOnOuterAdd=true` baselines; after a nested action, also check that exact target collection. Nested Add must leave at least `minRows` rows and pass every child-control check, while nested Delete may return a `createOnOuterAdd=false` target to zero rows. Never let an unrelated empty optional collection block the parent save, and never click its Add control or submit generated rows unless that nested Add was explicitly selected.
- Propagate a dynamic child's declared `maxLength` into `FieldDefinition.props.maxlength` and the bound `DomField.maxlength`, then bound free-text and enterprise-name generation before filling. Preserve a deterministic head and unique tail when shortening; never blindly truncate structured mobile, email, credit-code, date, or business-identifier values. Do not rely on browser truncation, because submitted/readback evidence and the persistence ceiling must receive the same value.
- A dynamic child's manifest-owned `probeValue` is a conservative quick-probe override, not a general test value. Apply it only when the current data strategy reports exact `probe` mode and the rendered child is empty; preserve hydrated values, and let standard or any other mode continue through its normal data strategy and boundary-failure contract.
- Run the final field-completion self-check only after nested preparation, validation repair, and unique-key preparation have produced the exact Save payload. For every submitted dynamic child with a declared `maxLength`, compare its string length to that persistence cap and block before clicking Save with the stable child path and observed/allowed lengths; accept both the canonical child path and a section-prefixed evidence key such as `对外投资.entInvestList.0.name`. Never send a known over-limit value and wait for an opaque HTTP 500. Apply this to both probe and standard modes: probe reports a save-precheck failure for smoke safety, while a standard `maxLength + 1` boundary input reports its own case failure without truncating, repairing, or saving that value.
- After filling a text or textarea control, read its retained input value. When a browser-enforced maxlength produced the requested prefix, use that retained value as submitted/readback evidence; any other mismatch is a fill failure. Cover both the accepted maxlength path and an unexplained stale-value mismatch.
- For a required nested Delete starting with zero rows, create and fill the retained legal baseline row through the same configured-row helper before creating and deleting the temporary row. Include the baseline submission in form-completion evidence and retain only that row's scoped nested evidence; never leave an empty row for the outer Save to reject.

## Declared Composite Unique Keys

- Before opening a physical Add form, capture a fresh configured list response and replay its real authenticated pagination request from page 1 through the reported total. Do not allocate from a partial page, stale prior response, missing-key record set, or guessed endpoint. If the current composite key is unoccupied, reserve it and keep every existing form value; change a field only when the current key is occupied or already reserved by this process.
- A list response may expose a business key under a display-oriented field rather than the submitted form code. Confirm every declared unique-key alias from the live response or read-only source contract and cover it with a response parsing test; do not treat an unknown or missing alias as an available key.
- Capture declared unique-key list evidence with one listener across a small bounded number of page reloads. Give every reload its own response start index and accept a snapshot only when all required list responses arrived during that same attempt; never combine partial responses from different reloads. If no complete attempt succeeds, stop before opening Add rather than manufacturing an unproved key.
- Replay every extra page from the captured Playwright `Request` object through `page.request.fetch(request, ...)`, changing only the page parameter. Do not construct a bare URL fetch: browser applications may inject authorization, tenant, or other request context that a naked replay loses. Reject any non-success response, inconsistent total, empty expected page, or duplicated/missing record identity instead of treating the partial result as availability evidence.
- Common-field Add transactions use the same pre-save preparation, but exclude every current Excel target field so boundary and validation inputs are never overwritten. When the primary repair field is protected, try configured alternate repair fields; choice alternates must be enumerated from real currently rendered options without changing the control before an unoccupied candidate is selected. Edit/Modify transactions skip both unique-key preallocation and duplicate-response repair entirely.
- The common save helper must enforce the Edit/Modify no-repair flag before calling the validation-repair callback. A duplicate returned by an edit save is a reported business error, never authority to mutate any existing field; keep a regression that makes the callback fail if invoked.
- Command-style Save/Submit uses the identical Add-only unique-key lifecycle: preallocate only for Add, commit after the confirmed successful business response before readback, and release on every earlier exit. Edit/Modify command cases neither preallocate nor repair a duplicate response.
- All ordinary and command save paths call the same structured business-validation repair interface with both the protected Excel codes and `allow_unique_repair`. Keep compatible test doubles on that keyword contract so a stale helper signature cannot hide a path that bypasses protected-field or Edit safeguards.

## Retained Dynamic Collection Readback

- A hydrated collection row that existed before the driver opened its Add form is retained business support data. The driver may fill its empty declared children so the submitted form is valid, but those child paths must not become mandatory detail/edit readback fields for the new parent record.
- Track these retained-row writes separately from collection wrapper codes. Default readback compares top-level writes and children of rows created during the current lifecycle; nested-operation evidence remains responsible for verifying the row explicitly created by the selected nested action.
- Partition required readback codes before every detail-JSON or reopened-edit assertion. Ordinary fields use the flat form/detail comparer; section-prefixed or array-index child paths use only the nested payload/table assertion. Never report a child-table path as a missing flat form control before its specialized nested assertion runs.

## Runtime Locator Diagnostics

- In a required-field recovery batch, excluded controls are intentionally absent from the initial error snapshot. Preserve their `skipped` outcome and compute later remaining validation errors only from non-skipped fields, using a guarded snapshot lookup; never index `initial_errors` for a skipped field and turn a non-applicable control into a framework failure.

- When a common-field target cannot be resolved, report the current no-value form inventory of runtime business code, label, control type, and selector. Diagnose from that inventory before changing a locator: distinguish an absent/conditional field, an identity-mapping failure, and a stale framework-generated selector; never require manual identification of the omitted field or use a prior `el-id-*` as a fallback.
- A module-scoped executor must be constructed without a page and bound to the current `browser_page` at each pytest item's start. Browser recovery may replace the Page between items; retaining a fixture-time page produces stale locators and false field failures. `bind_page` remains responsible for releasing pending unique-key reservations and clearing stale form state.
- When that scoped inventory is empty, append no-value form-context evidence: visible dialog count/type, per-dialog editable-control count, page-level editable-control count, visible form count, and whether a dialog is session-pinned. This establishes whether the error is a locator mapping issue, a stale scope, or an actual no-control render without collecting business field values.
- Form-context diagnostics should use Playwright locator counts for the active scope, visible dialogs, page-level editable controls, and visible forms, so evidence remains available while a framework navigation or render destroys browser `evaluate` context. Field-hydration timeout errors retain the last full no-value locator/context diagnostic rather than discarding it behind a generic timeout.
- A new form session may contain a visible empty dialog shell during transition. Select and pin the new dialog only after it is visible, distinct from the old generation, and contains a visible editable control; otherwise continue waiting. Do not attach a session marker to a loading mask or empty wrapper, because scoped field scanning will falsely report every field as absent.
- A Vue/Element rerender can later replace an already pinned form node. If its scoped scan becomes empty, enumerate current visible editable form instances and rebind only when exactly one exists; then update both the session scope and the driver scope before any fill, save, or readback. Zero or multiple candidates remain an explicit context failure, never a first/last fallback.
- Rerender recovery diagnostics may expose only control identity and render metadata (tag, type, stable code/name, visibility, dimensions, readonly state, and hidden ancestors), never entered business values. Search dialogs first; consider visible form containers only when no editable dialog exists, and de-duplicate a dialog/form wrapper for the same physical form before enforcing the exactly-one rule.
- After a legal baseline can trigger a second component hydration, resolve ordinary input targets through the bounded current-field wait rather than one immediate scan. That wait must reuse the same unique-context rebinding rule and fail with the runtime field inventory only after its deadline.
- Context recovery prefers a unique editable dialog. Only when no editable dialog exists may it consider visible form containers; do not merge nested dialog/form candidates into one count, because one physical form can otherwise look ambiguously duplicated.
- Apply the proactive rerender scan only to real Playwright locator scopes that expose `evaluate`; minimal unit-test form doubles retain their explicit operation contract and are not a substitute for DOM-context recovery evidence.
- Keep contract coverage for both a marked closing dialog followed by a real editor and the no-new-editor timeout. Test doubles for a real candidate must expose the editable-control contract; a visible wrapper alone is intentionally insufficient.
- A backend duplicate response may retry only when configured message tokens identify one declared composite constraint. Carry the same protected-code set into response-driven repair, update `submitted` before collecting markers/diagnostics/readback, and record the repair in `validationRepairs`. Release a pending process reservation when UI fill or save fails; ambiguous duplicate messages and exhausted candidates remain failures.
- In an Add common-field transaction, an explicit duplicate response for one declared composite key may temporarily authorize only that transaction's current Excel target when it is itself a declared repair field. Treat that response as authoritative even if the earlier list snapshot showed the key free, because the snapshot can lag a concurrent/new record; allocate a fresh unoccupied candidate instead of resubmitting the same key. Retry by changing that single target only; keep every other protected Excel value, including declared alternates, unchanged. This exception never applies to Edit/Modify, command cases, undeclared constraints, or ambiguous messages.
- A common-field Add starts from a valid filled baseline. Do not preallocate a composite key by modifying any already-filled baseline field, including a non-target alternate. Leave the original values for the first save; only an explicit declared duplicate response may authorize the single-target retry above.
- Emit a sanitized unique-repair decision line for duplicate save responses: form code, declared-constraint match, submitted field-code set, field-code membership, and protected/retryable code sets only. Never log submitted values, DOM text, request payloads, or credentials while diagnosing the repair path.
- Common-field validation must load its runtime field manifest into the driver's source-identity hints. When Element Plus regenerates `el-id-*`, map it to a stable manifest code only through the matching rendered label/control contract, never through DOM position or a reused numeric ID suffix such as `-46`; this stable identity must flow through baseline fill, composite-key detection, retry, diagnostics, and readback. If code/label/control identity cannot be re-proved after rerender, report a locator adaptation failure instead of clicking the sole control whose generated suffix happens to match.
- Edit-form readback follows the same identity rule: a generated runtime ID may claim a business code only when `_runtime_identity_for_dom()` marks the mapping `identity_safe`. A semantic numeric source may be claimed only by a text/number control, and two independently trusted controls claiming one business code are an explicit identity ambiguity rather than a last-value-wins comparison.
- When a created form has no automation-name field and its list hides the returned business ID, non-destructive readback may pass a separate auxiliary identity to row opening only when at least two stable submitted display values all match exactly one rendered row. Compare each value as exact normalized text or finite Decimal equivalence for formatted numerics. Do not replace normal record markers with these values or pass them into unrelated edit/detail paths. This auxiliary identity is for verification only; delete continues to require its registry ownership and request-ID safeguards.

## Detail Parent Data Provisioning

- Common-field discovery, validation, and batch entry points must share the same detail-parent selection contract as module actions. For project progress, that contract is the first row from the first non-empty project-status query; do not construct a parent or call a separate eligibility API. If every configured status query is empty, let the single explicit parent-precondition failure stop discovery and therefore prevent dependent validation commands from being scheduled; do not relabel it as a skipped test.
- A project-progress parent-precondition failure must propagate from common-field discovery. Validation and batch code must not retain an old precondition cache entry or convert that failure to `pytest.skip`.
- A related prerequisite form that must advance workflow state may use the normal add driver with `submit=True`, which selects the exact visible `提交` footer command. Ordinary Add and provisioning continue to use `保存/确定`; never silently fall back from an expected submit command to save.
- For `requires_business_id=True`, first use an existing parent-list record. Provision exactly one automation-owned parent record through the standard add/save driver only when the parent list is stably empty, or every bounded existing candidate has entered the target child module and its rendered table explicitly says `暂无数据`; do not create records for permission, route, or component failures.
- A `provision_only=True` parent or child creation is an explicit add-flow request. It must run the add/save driver even when the selected detail action is Edit and therefore has no `EI_REQUIRE_ADD` flag; returning `page_access` is an invalid provisioning result.
- Carry the returned business ID and automation record markers into detail navigation. When the first usable parent is an existing record, capture one uniquely rendered business ID, row key, or business-name value before clicking it. Cache only that stable identity, never a DOM locator, and re-find the exact row/card whenever a terminal transaction needs a fresh form; do not rescan the bounded candidate set after a cache hit. Invalidate and rescan once only when the exact cached identity is proven absent; ambiguous matching remains a precondition failure.
- Reuse that exact parent record for later actions in the same batch whether it was provisioned or selected from existing data. If provisioning or first selection cannot yield a stable unique identity, keep the bounded safe-selection path; never silently fall back to an unrelated first record after an exact identity has been established.
- When a persisted parent ID is not on the first rendered parent-list page, traverse authenticated rendered pagination and locate that exact ID before failing. Do not substitute a visible row, marker, or page position; absent or duplicate ID remains a precondition failure.

## Reusable Delete Records

- A delete response followed by an inconclusive rendered-list absence check may use the same-resource `detail/{id}` endpoint as read-only evidence. Start with the request context, but when it returns HTTP 401/403 retry through `page.evaluate(fetch)` in the active browser page so local-storage authorization and same-origin cookies are preserved. Only HTTP 404 or an explicit business not-found response proves deletion; HTTP 401/403 after retry, HTTP 5xx, malformed JSON, and transport errors are verification failures, never deletion success.

- Treat the local automation-record registry as the only cross-run ownership proof. Immediately after an Add response is business-successful and returns a business ID, before list/detail/edit readback, write or replace the entry keyed by normalized `page_scope + business_id`; retain only submitted display values, an automation marker when available, and the minimal ID-associated response fields. A later readback failure must not erase this successful-create evidence. Never register Edit/Modify/Update saves, including common-field edit transactions. Every module-smoke and common-field entry point must pass the shared registry path, and common-field Add must pass its stable entry-page scope rather than the post-save detail URL.
- On a later delete run, consider only entries loaded from the current normalized `page_scope`; a visible `AUTO_`/`UI自动化` marker plus business ID without that scoped entry is not ownership proof. Associate the registered business ID to exactly one visible row by its exact rendered ID. If the list hides the ID, require either the ID-associated response fields or at least two exact saved display values to match one and only one row; a marker alone never permits the hidden-ID exception. A regular business row, an unregistered ID, a different-scope entry, a one-field/partial match, or an ambiguous association is never eligible for deletion. Remove only that `page_scope + business_id` entry after the guarded delete response succeeds and the same record is proven absent; cancellation or any failure keeps the entry.
- Response-to-row association must keep all nontechnical record display scalars as evidence and require every selected scalar to match one visible row; do not introduce field-name exclusions for ordinary business display fields merely to fit one page. Page-specific mismatch must be resolved by an explicit associated response or stable two-field identity, never by weakening the unique-row rule.
- Association helpers may receive either a live Playwright locator or a pre-expanded iterable of rows. Detect a locator only when it exposes callable zero-argument `count()` plus `nth()`; a Python list's `count(value)` is not locator evidence. This keeps delete reuse and readback on the same exact association rules.
- A page may omit business IDs from list rows. After the exact target row has already been uniquely proven by response association or at least two exact saved display values, the row pin may omit its ID only for that proven result; keep the independent delete-request ID guard and response-ID assertion mandatory. A marker-only match, partial display match, or ordinary visible row must still fail before any delete click.
- Cover this hidden-row-ID exception with a contract test that asserts `allow_missing_id=True` is passed only for the exact response-associated or full saved-display identity, preserving the default refusal for every other delete locator.
- Before reusing an automation-owned delete record, call `count()` on the visible loading collection before selecting `.first`. A zero-match collection, including test doubles and rendered-empty lists, is ready rather than a loading timeout. The current-scope registry entry is mandatory even when a visible row exposes both an automation marker and a business ID.
- Before clicking Delete, pin the uniquely located rendered row and re-read its business ID from the pinned row. Only click its row-local Delete button when it still equals the expected saved ID; keep the request-ID interceptor as a second independent guard. If either proof changes or is unavailable, stop without deleting.
- Preserve the save response and any exact-ID detail/list response as record-identity evidence on every successful readback return path, so a later delete has the same proof source. When a visible row exposes no business ID, associate it from that evidence only with at least two stable rendered display values that all match exactly one row. Treat formatted numeric values as equivalent only when their finite `Decimal` values match. Reject one-field, partial, zero-row, or multi-row associations; never select by score, position, or first/last fallback. Keep the delete-request business-ID interceptor active even for this response-associated row.

## Business-ID Row Contract

- When the user explicitly authorizes an application-side identity contract, a dynamic table's View, Edit, and Delete row actions must bind the record's existing backend ID as `data-business-id`. The smoke driver reads that exact attribute from the row or one of its action nodes before any text-based fallback; missing, duplicate, or conflicting IDs remain a locator failure.

## Element Plus Date Picker Interaction

- For `DATE` and `DATETIME` controls, use the shared `FieldInteractor` to open the visible Element Plus picker, navigate by its rendered month controls, and click the exact enabled date cell. Do not use `fill()` as a fallback for a valid date value.
- After selecting a date, verify the input contains the exact year, month, and day. The picker must be hidden before any subsequent command; use its footer confirmation when present, then `Escape` only as a bounded fallback, and fail explicitly if it remains visible.
- For `DATETIME`, retain the caller's original submitted representation after the date-cell interaction so downstream readback still retains its time expectation.

## Command Save Readback And Diagnostics

- When identifying a business mutation response, exclude attachment and file-list endpoints such as `savefilebatch`, `selectcommfilelist`, and storage/upload paths before applying the add/save/create/update candidate rules. Attachment traffic must not be mistaken for a successful business save.
- After obtaining a save business ID, request the uniquely source-declared GET detail endpoint before any rendered-record lookup. Build it from the declared query/path ID binding and deployment API prefix on the Save response origin; only when that contract is unavailable or unusable may the shared helper infer `detail?id={id}` and then `detail/{id}` from the mutation URL. Require the exact requested ID in both URL and successful JSON response, then compare every required stable submitted field. A complete exact-ID JSON match is terminal save evidence; an ID-associated list response may prove presence but must never suppress this readback merely because the rendered table hides the ID. Never treat a generated `el-id-*` field as stable readback evidence; distinguish an explicitly empty specialized readback set from a normal source set that becomes empty after generated-ID filtering. The explicit empty set may delegate to a specialized verifier, but a normal set that filters to zero must fail even when the detail response contains the exact business ID: identity proves which record was read, not that any submitted value was persisted.
- Extract the primary business ID only from direct response fields or one-record `data`/`result`/`body`/`content` envelopes. Reject conflicting IDs, multi-record envelopes, and IDs found only in child tables or attachments; never recursively accept the first generic `id`. Every Add/provision transaction must stop when that unique ID is absent and must not replace it with a name, marker, list prefix, or row order; only an explicitly associated existing-detail Edit may retain its already established record identity when an update response has no body. Detail GET starts through the request context and retries only HTTP 401/403 through the current page's authenticated `fetch` context. Classify endpoint absence, request-context failure, transport/HTTP/JSON/ID rejection, and incomplete field mapping as `automation_detail_adapter`. Diagnostics may log only that fixed classification, GET, query-free path, HTTP status, and a fixed failure kind; omit query values, response/request bodies, headers, Cookie, Token, and storage state.
- An associated detail JSON response is evidence of record association, not automatically a complete field readback. If it returns none of the submitted comparable fields, continue with rendered detail and reopened edit-form readback; still fail if those UI sources cannot compare the required fields.
- When an edit save returns to a list that hides the business ID, associate its ID-bearing response record through source-discovered form field codes and their declared display aliases only. Prefer a display alias such as `belongSectionName` over its stored code, discard candidate values not rendered by any current row, then require at least two remaining display values to match exactly one row before opening Edit; formatted finite numerics may match by their `Decimal` value. Do not require hidden raw codes, row versions, audit fields, or other response-only scalars to appear in the list. This scoped rule is only for non-destructive edit readback; delete ownership and row selection must keep the default full-evidence association contract in `Reusable Delete Records`.
- For an independent Edit/Modify case that is not required to reopen the just-created record, prefer a freshly mapped newest enabled row; when the list JSON cannot be mapped to a rendered row, open one currently visible row with an enabled row-local edit action. Report that fallback as an existing-row operation. Do not use it for Add UI identity proof or for guarded automation-owned deletion.
- A command-only Save/Submit case must compare only its explicit `required_codes` (normally the stable record identity). Do not compare unrelated submitted relationship IDs with the select's rendered display name. Full input-correctness and optional-clear cases retain their explicitly requested complete readback.
- A Save/Submit feedback or rapid-click case must establish one real valid field change before clicking when the opened edit form is already fully populated. Use a traceable `AUTO_SAVE_` value in a writable text/textarea field, then require one business mutation response. If no response is matched, report sanitized method/path/status for mutation requests and `requestfailed` events, never request bodies, cookies, tokens, or credentials.
- For an optional-value-clear command case, manually remove one populated ordinary optional value first (text, select, radio, etc.). Only when no ordinary optional value is available may it delete a populated optional attachment through that field's own row-scoped delete UI. Do not fail a successful value-clear merely because an unrelated attachment has no delete control.
- A common-field batch may share one browser session for one module and operation, but it must retain the existing transaction planner as the physical isolation boundary. Discover the current runtime manifest once and execute each planned transaction in order. After an ordinary case-specific failure, close the unsafe form, record `execution_failed`, and continue later transactions. When form-context creation or a rendered dynamic-collection contract raises an explicit shared-precondition failure, execute it once, stop opening forms, and map `blocked_by_shared_precondition` to every remaining Excel binding. A result-count mismatch is likewise batch-fatal. The regular launcher path must use parametrized `tests/test_common_field_validation.py`: create one pytest report item and one Allure result per bound field, including every member of a required-field transaction. Every item reads only its own indexed result from a module-scoped transaction cache; the cache must execute the physical transaction, form opening, and Save at most once.
- A fresh Add may open a Dialog/Drawer or switch a visible detail container from read-only to an editable inline form. Mark only pre-existing visible forms that already contain editable controls; then accept a new editable Dialog/Drawer or inline form. Do not reject an inline form merely because its DOM node existed while it was read-only.
- Compatible accepted attachment cases in the same module action, opened form, scenario family, and branch conditions use one `attachment_persistence` transaction: open and baseline the form once without optional uploads, upload every target attachment in that field's own owner, issue exactly one business Save, then reopen/read back each attachment independently. Keep one pytest/Allure result per Excel binding and include its uploaded name, previous names, transaction ID, and `shared_save=true` evidence. Isolate required-attachment validation, removals, cancel/close/submit workflows, different branches, conflicting lifecycle expectations, and any attachment operation that changes form context. A shared Save failure may affect all transaction members, but upload and readback failures must remain attributed to their own attachment field; never use a successful Save alone as attachment persistence evidence.
- Use an explicit mixed transaction model inside that batch. Accepted reversible text, textarea, number, amount, and percentage boundary cases in the same conditional branch use `probe_persistence`: open and baseline one form without optional attachment uploads; apply each value, verify the exact control value and absence of visible validation, then restore the original value. Observe POST/PUT/PATCH traffic through the shared business-mutation matcher during every probe, the post-restore quiet window, and the final representative-value rewrite; any business write before the explicit Save makes the form unsafe and fails the transaction, with diagnostics limited to method and URL path. After all probes, keep the last accepted representative for each real field and perform one normal Save/readback. Treat all required readback codes in an ordinary merged transaction as protected Excel targets during declared unique-key preparation; command transactions still exclude no target because their fields are synthetic commands. Report the representative Excel binding as `saved_verified_and_retained` and earlier bindings as `form_probe_passed`, so every workbook binding remains an independent pytest/Allure result even though the physical form and persistence operation are shared. Keep required validation, invalid input, security/safe-content, whitespace persistence, choices, attachments, commands, branch-changing cases, and any non-reversible workflow in isolated or ordinary persistence transactions.
- A reversible probe merge key must include rendered field family, scenario family, conditional branch, and the full input-constraint fingerprint (`maxlength`, `maxDigits`, `precision`, `min`, `max`, `step`). Do not merge numeric, amount, percentage, and textual controls merely because their branch matches. For decimal max-digit values, `maxDigits` excludes the decimal point while HTML `maxlength` includes it; accepted boundary generation must use their strict intersection so the control cannot silently truncate a supposedly valid value.
- If a probe fails before its shared Save, attribute `execution_failed` only to the binding that triggered the exception. Return `blocked_by_transaction_failure` for later unexecuted bindings with the root case ID and error, and surface those report items as skipped rather than duplicating one failure across the batch. Probes already restored before that point remain `form_probe_passed`; do not claim persistence for them.
- For dynamic collection required validation, normalize runtime row keys such as `financeSources.0.fundsPlan` to the manifest wildcard key `financeSources.*.fundsPlan` before reconciling the post-submit required-error snapshot. Read the field-owner inline error; a global form message does not prove the dynamic field has a valid field-level prompt.
- For EDIT-010 required-field validation, observe business mutation requests from before clearing the field until after submit. Fail any write triggered by clear/blur. After submit, skip a target only when it remains rendered and explicitly becomes non-required; a disappearing field is not evidence of conditional deactivation. Reconcile every active dynamic-row instance through its wildcard manifest path and require at least one field-level required prompt.
- Keep module-scoped common-field executors page-neutral until a function-scoped recovered browser page is available, then call `bind_page()` in each report item. Do not call the browser runtime while constructing a module fixture, because pytest caches a fixture setup failure and converts one navigation outage into every parametrized field failure.
- Attachment persistence may share one upload/save/readback lifecycle only for distinct attachment fields in the same scenario family and conditional branch; retain one indexed pytest/Allure result per Excel binding. For ordinary accepted or field-error persistence, merge only distinct fields of the same rendered field family, scenario family, expected-result type, and branch; unrelated rules remain isolated so a single validation failure has correct attribution.
- Keep transaction-planner regression coverage in `tests/test_common_field_cases.py` for the isolation keys above, and executor coverage in `tests/test_common_field_executor.py` for stable runtime field identity. A generated DOM ID must not be mapped by source order when its normalized label and control kind disagree with the source field.

# 通用模块新增冒烟

## 事实来源

- `src/ei_ui_smoke/module_driver.py`：通用新增、保存、业务成功判断和详情验证主流程。
- `src/ei_ui_smoke/source_form.py`：沿 Vue 组件引用发现自定义表单字段。
- `src/ei_ui_smoke/dom.py`：扫描当前可见表单字段。
- `src/ei_ui_smoke/interactions.py`：输入、选择、日期、单选、上传等交互。

## 执行闭环

- 字段“已定位、已填写”只证明控件非空，不代表提交值的业务类型正确。保存前必须核对运行时控件类型与生成值；对 `type=number`、`inputmode=numeric/decimal`、数字组件，以及标签或稳定字段码明确为比例、金额、出资额、数量、价格、回报率、期限、周期等数值语义的文本控件，首次填写就按 `number` 生成可解析数字，不得填入通用随机文本。占位符缺少单位时仍使用字段码后缀补充判断，例如 `buildPeriodMonth` 必须生成正整数；同时保留建设内容、建设规模等非数值文本反例，防止按共同前缀误判。保存后的校验修复只能作为未知约束兜底，不能替代首次类型识别。通用字段 manifest 可能复用旧扫描产物，加载 manifest 时也必须使用同一数值语义规则二次归一化，避免旧 JSON 把业务数字字段继续按文本执行。
- 通用字段执行器只为真实新增/添加/新建表单进行唯一键预分配与重复值修复准备。通过 `EI_COMMON_FORM_ACTION` 打开的非新增表单，即使名称不是“编辑”，也按既有记录修改处理，禁止改写唯一键或制造新增标识；仍需使用该真实动作打开表单并完成保存/回读。
- 保存接口返回 HTTP 5xx 时不得立即归类为外部阻塞。先对照失败截图、已提交字段的类型和页面约束；只有提交数据已符合控件与业务约束，且同一真实操作复跑仍由服务端返回 5xx，才能作为有证据的外部阻塞。
- 保存接口返回 HTTP 4xx/5xx 时，在原响应摘要之外记录脱敏请求结构：只允许字段路径、JSON 类型、数组长度和是否截断，不得记录字段值、完整请求体、查询参数或凭据。用该结构先核对重复列表、空数组、嵌套对象和部署 DTO 形状；结构证据不足时不得根据 `SYSTEM_ERROR` 猜测字段并反复改测试值。
- `field-diagnostics` 的 `status=passed` 只证明保存前字段定位/填写检查通过，不证明已经点击保存、保存成功、取得主键或完成详情/编辑回读。最终状态必须以目标 CRUD pytest 的 Allure result 和 `ModuleSmokeResult.mode` 为准；缺少目标用例 `*-result.json` 时只能报告结果不完整。

1. 使用运行时菜单提供的真实路由进入模块并确认页面没有登录失效、404 或应用级错误。
2. 查找可见的新增/新建/创建入口。点击后以当前可见对话框或表单区域为主要作用域。
3. 用 `discover_custom_form_fields()` 读取 Vue 源码中的字段契约；用 DOM 确认字段是否实际渲染和定位。源码不替代浏览器交互。
- 当列表页同时声明新增、编辑、入库或跟进等多个弹窗时，字段契约必须优先来自明确的 `openAdd`/`openCreate`/`openNew` 处理器中的静态 `componentPath`；不能把与新增无关的弹窗并入候选而丢失稳定字段码。未声明唯一新增处理器时保持未解析，禁止按目录或 DOM 顺序猜测。
- 把源码可证明的直接条件提取为分支候选；复杂条件只保留其中可识别的表单模型 driver 作为运行时探测提示，不计算表达式结果。直接 CRUD 必须枚举当前部署页每个可见 driver 的真实可选值；二级 driver 仅在先应用其上游分支条件后枚举，已位于条件路径中的 driver 不得作为新受影响字段再次入队。源码条件码值与页面显示值无法直接匹配时，逐个应用父 driver 的真实选项，以子 driver 是否出现确认映射，禁止把源码码值当显示文字强点。每个有效分支使用新的新增表单事务，依次完成当前分支基线、保存、业务主键提取和详情回读；前置数据构造、删除准备和嵌套动作不扩展为全分支执行。
4. 每次联动或响应式重渲染后重新扫描 DOM，禁止继续使用可能失效的旧 Locator。
- 联动选择后同时等待相关 XHR/fetch 结束、全局/表单 loading 消失和稳定窗口内字段签名不变；旧表单实例被替换时只能重绑唯一的新可编辑表单。重建基线前删除已从当前分支隐藏的旧字段提交证据，再补齐新分支字段；被测字段和所有活动 branch driver 始终受保护，唯一名称生成、重复值修复和基线默认值都不得覆盖它们。
5. 首次扫描时按稳定业务字段码、可规范化标签和控件类型建立普通字段执行计划。每次交互后的重扫必须按该计划身份重新定位当前字段，禁止用新的 DOM 数组下标替换计划项；新出现且身份可判定的条件字段追加到计划末尾。身份不唯一或字段已消失时停止该项，不得填入当前同位置的其他控件。动态集合保持行级执行，只填写新建行的空子字段并保留已有业务值。嵌套操作执行器一次只接受一条路径；多条路径必须在调度层拆成独立父表单事务，不能在驱动内合并。回归必须覆盖重渲染插入字段后仍按原计划执行，以及驱动拒绝合并路径。
6. 使用 `FieldInteractor` 处理输入、数字、日期、单选、下拉、远程选项和附件。下拉值从页面真实候选项选择，不向选择框强行填任意文本。
6. 对公司到部门、部门到项目组等依赖下拉执行回退和重选，直到得到完整可保存组合或明确失败。
7. 点击保存前开始捕获响应；从 `/add`、`/save`、`/create`、`/insert` 等候选中选取实际保存响应。
   新增表单存在已确认的组合唯一键时，在收集记录标识和点击保存之前应用声明式唯一值；编辑动作不主动改动组合键，只有后端返回明确重复提示时才进入受控修复。
   编辑页的真实保存也可能使用 `/update`、`/edit` 或 `/modify`。所有新增、编辑和公共字段执行器必须复用 `ModuleSmokeDriver._is_business_mutation_url()` 的同一候选规则，再排除附件等非业务变更请求；禁止在某个执行器内维护较短的 URL 白名单，否则页面已保存时会被误报为“未捕获响应”。
   当提交载荷经过前端归一化、无法与表单基线值直接相交时，先比较提交字段的稳定叶子键与候选请求载荷键的交集，以最大键交集区分主业务更新和动态表单、附件等伴随更新；只有仍无值或键证据且排除附件后仅剩唯一业务变更端点时，才允许唯一端点兜底。多个不同端点仍无法区分时必须失败，禁止按最后一个响应猜测。
8. 同时检查 HTTP 状态和响应体业务状态。HTTP 200 但业务码失败时必须失败。
9. 用 `extract_business_id()` 从响应中提取业务 ID；支持现有键集合，不在页面代码中单独写死 `fundId`。
10. 新增必须取得唯一业务 ID，并优先用该 ID 请求源码声明的详情接口核对提交值。名称、前缀、列表顺序和自动化标记不能替代主键；只有详情接口确实不可用时，才可继续在同一业务 ID 已精确关联的详情或编辑上下文中逐字段回读。
11. 每轮修复通过后执行“根因沉淀判断”：可跨模块复现、涉及公共组件/框架行为、改变通用诊断顺序或已出现两次以上的问题，写入本 Skill 的对应章节并补回归测试；仅属于单页临时 DOM、一次性业务数据、环境故障或尚未验证的猜测，不写入 Skill，只保留诊断产物。

新增入口可能同时保留隐藏旧节点、禁用节点和当前可操作节点。共享定位必须在每次解析时限定可见且可用的候选，再选择第一个候选；禁止先对包含隐藏节点的混合 Locator 取 `.first`。当 `EI_REQUIRE_ADD=true` 时，等待期内没有可操作的新增/添加/新建/创建入口必须明确失败，不得降级返回 `page_access`；主新增、嵌套新增和公共字段发现复用同一规则。

不得在第一次失败后结束。读取 `artifacts/field-diagnostics/latest.json`，按 `notLocated`、`notFilled`、`fillFailed` 修复并重跑同一模块；同时查看 `optionalNotFilled`、`optionalFillFailed`、`expectedNotRendered` 和 `validationRepairs` 了解非阻断空值、条件字段及校验修复历史。只有真实浏览器测试通过且诊断 `status=passed` 时停止；外部系统、权限或数据源持续阻塞时，保留最后诊断并明确报告阻塞条件。

不要假定新增表单一定在 Dialog 中。点击新增后先查找可见 Dialog/Drawer；没有时继续识别页面内嵌表单及其保存按钮。内嵌表单以表单隐藏、保存成功响应和成功消息作为完成信号，不能等待不存在的对话框关闭。

只有源码入口同时具备标准新增和提交闭环时，启动器才应设置 `EI_REQUIRE_ADD=true`。标签快捷编辑、纯配置、只读或仅修改页面执行页面访问检查；不要因为它们是运行时菜单叶子就强制要求新增。检测到标准新增入口后，保存失败仍必须失败，不能降级为页面访问通过。

## 成功标准

只有满足以下条件才报告“新增成功”：

- 快速重复点击保存场景中，第二次点击被 UI 禁止且只产生一次业务保存响应时，执行器返回 `rapid_click_blocked_by_ui`；这是已验证的防重复成功结果，公共字段验证入口必须接受，不能因允许结果集合遗漏该值而制造失败。

- 找到并提交了真实新增表单。
- 捕获到成功的保存接口。
- 响应体没有业务失败标志。
- 提取到唯一业务主键；新增成功响应缺少主记录 ID 时闭环失败，禁止按名称、前缀或列表顺序继续回读。只有调用方已从当前详情上下文建立业务 ID 的既有记录编辑，才可显式传入该 ID。
- 列表或详情至少一个最终回显来源确认记录及关键提交值。
- 保存后当前页若已能用业务 ID 或本次自动化唯一标识定位到唯一记录，且该记录行单元格、卡片或当前只读区域完整展示本次要求核对的全部字段值，则优先返回 `add_and_list_verified`，不要再强行打开详情页或等待编辑表单；字段缺失、值被截断/省略、重复记录无法唯一定位，或换行/空格/缩进不能按浏览器渲染文本精确证明时，继续走详情接口、详情页或编辑页回读。
- 详情/列表只读回读的字段标签要先规范化提示语前缀，例如 `请输入潜在风险分析` 与页面标签 `潜在风险分析` 视为同一业务字段；但仍必须先证明标签和值关联，禁止全页搜索预期值冒充字段级回读。
- Excel 明确声明“输入值正确性检查”且预期同时包含编辑页、详情页时，优先按保存响应业务 ID 请求同资源 `detail/{id}`。返回 JSON 的 ID 相同且所有稳定提交字段匹配时，直接以 `add_and_detail_verified` 完成，不遍历列表或打开编辑页；详情接口不可用、ID 不符或字段不完整时，才按一次事务执行详情页和编辑页回读。该兜底路径先用业务 ID 或稳定唯一值确认同一记录，禁止使用页面全局第一个“查看/详情/编辑”按钮。
- 详情页点击页面级“编辑”后，编辑表单不一定打开 Dialog；公共详情组件会在 `.base-info-page` 内把只读内容原位切换成 `.el-form`。同页可能还有附件等只读 `.el-form`，且只读到编辑的响应式切换会晚于按钮点击；打开/保存/双回读使用的表单 scope 都必须在有上限的等待期内重复扫描候选，锁定实际包含可见可编辑控件的表单，禁止按 DOM `.last` 或首次空扫描猜测。候选一旦确认包含可编辑控件，立即给该具体 DOM 元素写入唯一会话属性并改用属性选择器；不得返回 `nth(index)` 等位置 Locator，因为 Vue 重排后同一 Locator 会动态漂移到只读或附件表单。初始表单和保存后重新打开的编辑表单遵守同一固定规则。同时不要把页面任意搜索表单加入新增入口作用域。
- 详情接口完成不代表详情 DOM 已完成异步渲染。页面字段回读必须在有上限的等待期内重复扫描，直到本次全部目标字段和值匹配或超时；不得用接口返回后的第一次空扫描提前终止后续编辑页回读。字段和值既可位于相邻单元格/描述项，也可位于同一可见节点的“标签：值”文本中；两种结构都必须先证明标签关联再比较精确值，仍禁止用全页预期值搜索代替字段关联。保存后回读 helper 可能被单元测试、前置数据构造或降级诊断路径局部初始化调用；源码字段列表只能增强标签映射，不能作为必需状态，缺少 `source_fields` 时使用空映射继续通过提交字段码回读。
- 详情/编辑/列表共用的回读值比较 helper 应保持类级纯工具契约，可被断言函数和单元测试直接通过 `ModuleSmokeDriver` 调用；若 helper 内部使用 `cls` 访问规范化或数值语义方法，必须声明为 `@classmethod`，不要无意改成需要完整 driver 实例的普通方法。
- 普通保存用例仍沿用详情或编辑页任一来源完成回读，不得把双页面全字段要求扩散到未声明该预期的用例。若记录入口先打开只读详情且没有可用详情 JSON，必须识别并点击当前记录的页面级“编辑/修改”按钮，等待真实可编辑表单出现后再做编辑回读；只读 `.el-form` 内偶然存在 enabled input、文件控件或框架内部控件，不足以证明已经进入编辑态，也不得直接等待它变成编辑表单。

仅打开页面时结果应为页面访问类结果，不能写成新增成功。找不到新增入口、保存响应，或既无业务主键也无稳定唯一值时必须失败并说明停在哪一步。

## 详情模块

- `requires_business_id=True` 的详情节点先从列表已有记录或本次新增结果取得 ID。
- 运行时详情树使用的 `*/detail` 可能只是自动化合成入口，并非部署系统可直接访问的真实路由；禁止把它当普通页面直接 `goto()`。先打开父列表，通过真实卡片或表格记录进入详情，以页面最终产生的路由、业务 ID、session state 和查询参数为准；直达后落入 `#/404` 属于前置路径错误，不是模块页面 404。父列表记录没有“详情/查看”按钮时，先在该记录内部寻找可见可用的业务名称超链接进入详情，再考虑整卡/整行点击；禁止全页寻找第一个同名链接。若点击记录后 URL 未变化但当前页已经渲染目标详情菜单、目标组件或目标操作，则当前列表可视为详情承载页，继续在当前页执行详情校验，不得强制要求路由变化。
- 卡片列表和表格列表分别按现有 `module_driver.py` 行为打开详情，不假定所有模块都有表格行。
- 进入详情首页不等于进入目标详情模块。根据运行时完整层级提取“详情”之后、操作名之前的分组与子模块，按页面实际页签/纵向菜单逐级点击；每级等待可见和组件渲染，最终必须看到目标操作或目标组件证据后才能执行，禁止停在默认详情首页后用全页同名按钮兜底。
- 父列表第一条记录可能因业务阶段、权限或数据完整性不具备目标详情子模块。使用有上限的候选记录重试：候选序号必须是跨分页的绝对序号，依据当前页大小跳到对应页后再取页内记录；禁止每次回到第一页后把“前 N 条”误当成全列表重试。目标操作已可见但处于禁用态时，给予短暂异步渲染宽限后立即换下一条记录，不为每条业务阶段不适用的数据等待完整操作超时。默认扫描上限由 `EI_DETAIL_RECORD_SCAN_LIMIT` 控制，目标模块出现后停止；候选耗尽时报告尝试数量、最终 URL、缺失层级、操作禁用状态和可见活动菜单，不得无限循环，也不得把某条数据不适用误报成模块未采集。
- 当详情模块的只读业务前置门禁已证明候选父记录全部不适用时，新增、编辑、删除、字段发现及字段验证均报告明确跳过，不再继续打开表单或将业务门禁归类为字段/定位失败。参数化字段验证在同一 pytest 进程缓存该原因，使后续字段行直接跳过；未知门禁响应、请求异常、权限或详情导航异常仍保持失败。
- 详情接口 URL 不一定包含业务 ID；允许结合请求体和最新详情响应识别，但必须排除保存响应自身。
- 保存成功后的列表刷新或子记录查询接口即使 URL 不含 `detail/getById`，只要它是成功的 JSON XHR/Fetch、请求或响应标量精确包含本轮业务 ID，并且字段级回读断言能在该 ID 对应的同一逻辑记录内核对目标提交值，就应先作为持久化证据；禁止在读取已捕获响应前强制要求 DOM 行暴露业务 ID。仅响应中出现 ID 不足以通过，目标字段值不一致仍须失败；关联响应不含全部目标字段或不返回嵌套子表时，只保留其已经证明的记录身份和字段证据，并继续走完整页面详情/编辑回读，不得把局部列表响应当成完整详情而直接通过或失败。
- 当输入正确性用例还要求编辑回读，而父详情只展示无业务 ID 属性的子表行时，可用上述 ID 关联响应作为详情证据，再将该响应记录的显示字段与每条可见行的单元格做精确组合匹配，唯一关联后仅点击该行的编辑/修改入口。零匹配、多行最高匹配并列或字段值只能模糊包含时必须失败，禁止按第一行、最后一行或新记录通常置顶来猜测。
- 记录容器的稳定业务 ID 既可来自行/卡片自身的 `data-key`、`data-row-key`、`data-id`、`data-record-id`、`row-key`，也可来自其内部真实查看/详情/编辑/修改/删除/移除命令节点的同名属性。打开、响应关联与删除必须复用同一解析规则；只允许业务命令节点贡献记录 ID，避免把附件或下载按钮的对象 ID 当成记录主键。目标 ID 命中多条记录，或同一容器的行属性与命令属性暴露不同 ID 时必须停止，禁止再以重复显示字段或列表顺序猜测。
- 父详情内嵌子表没有名称/标题等标准记录字段时，保存响应的子记录 ID 及其关联 JSON 仍是首要关联证据。仅当表单不存在标准记录字段时，才可按已解析的运行时业务字段码，为已明确以 `AUTO_` 或 `UI自动化` 开头的文本/文本域追加一次性保存 token，并将该值作为 DOM 定位回退；不得把普通描述字段升格为标识。回退标识必须精确匹配唯一子行，重复匹配仍失败，不能取第一条。
- 详情响应候选必须同时满足：HTTP 成功、请求资源类型为 `xhr` 或 `fetch`、响应 `content-type` 为 JSON。禁止仅因静态资源文件名包含 `detail` 就选中 CSS/JS/图片。
- 不要假定详情业务接口一定包含 `/detail`、`getById` 等字样。先在真实页面点击详情并记录点击后产生的 XHR/Fetch，再将确认包含业务字段的稳定接口纳入匹配。例如建设项目详情数据来自 `/fi-service/projAppInfo/listPage`。
- 详情接口返回编码或 ID、详情页或编辑选择框显示名称时，用成对字段校验：接口字段可以匹配自身原始值或对应名称字段；详情与编辑页面的回读期望都必须取同一详情记录中的名称字段，不得拿提交 ID 与页面名称直接比较。详情 JSON 没有返回时，在点击保存前从本次表单的同一 select/radio/checkbox 控件采集显示文字，并与该字段本次提交的存储值成对保存；只有存储值仍精确匹配时才允许作为页面回读期望，防止复用表单或重试后串用旧显示值。详情 payload 中的名称字段优先级仍高于表单采集值，且该机制只用于已登记稳定 code/name 别名的选择字段，不放宽普通文本比较。当前建设项目映射为 `projClassify` → `projClassifyName`、`belongSection` → `belongSectionName`、`inveId` → `inveName`。Purvar 只读表单常把标签渲染为 `.purvar_form_item` 第一列中的普通 `span`、值渲染在同一行 `.purvar-col__content` 中，字段级详情定位必须覆盖此结构。
- 投资人库确认了同一通用规则：`investorType` → `investorTypeName`、`company` → `companyName`。新增映射前先用真实详情响应确认字段语义，再集中加入 `display_aliases` 并补测试，不按页面散落特判。
- 管理员、组织和状态字段沿用同一规则，例如 `registrationStatus` → `registrationStatusName`、`orgId` → `orgName`。布尔值、`0/1` 等码值与“是/否、只读/可编辑”等页面文字的转换必须集中维护并用真实响应形状测试，禁止在单页驱动中临时放宽字符串比较。字段码具备通用布尔语义（如 `is*`、`has*`、`need*`、`*Flag`、`*Status`）且提交显示值为“是/否”时，详情接口返回 `1/0/true/false` 应按布尔等价比较。
- 页面提交的是显示文字、详情只返回数字 ID/码值且没有对应名称字段时，不得直接拿显示文字与数字值比较。若该字段已登记稳定的显示名称别名，并且同一稳定字段路径在本次真实保存请求中提交的 ID/码值与详情值一致，则接口层按存储值持久化通过，同时继续用详情/编辑页面核对用户选择的显示文字；不得硬编码 `1=某名称`。保存请求没有同路径值、码值不一致或字段未证明是显示值/存储值语义时仍判为不可比较，不能放宽普通文本字段。
- 比较嵌套列表响应时，检查所有候选记录中的原始字段和名称字段，不要固定读取第一条记录的第一个同名字段。
- 当页面已经显示新增成功并进入详情，但用例仍失败时，先读取本次最新模块日志中的最终断言。区分“保存失败”“详情接口识别失败”和“详情值表示形式不同”，不要把自动化校验误报描述为业务新增失败。

## 运行安全

真实浏览器测试可能创建以 `AUTO_` 开头的业务记录。运行前明确告知用户会写入已部署系统；没有授权时只运行本地契约测试。

通用字段新增校验在保存和回读完成后保留本次自动化记录，不得把删除作为正向用例或异常保存用例的自动清理步骤；执行结果使用 `saved_verified_and_retained` 等明确保留语义。只有用户选中删除、移除或清空等显式业务操作时，才进入独立删除验证流程。

同一 pytest 会话连续执行通用字段事务时，可恢复的校验阻断继续复用原表单实例；只有上一事务已保存/提交、取消/关闭、跳转、实例替换、恢复失败或异常污染时才关闭残留表单。终结后若当前页已进入上一条记录详情，先返回启动器传入的 `EI_ENTRY_URL`/`EI_FORM_URL`，再查找新增入口。不得依赖删除清理顺带返回列表，也不得在详情页把“找不到新增按钮”误报为下一条用例的字段问题。

保存接口成功后继续按原表单实例等待页面完成关闭或跳转，超时上限允许通过 `EI_COMMON_FORM_CLOSE_TIMEOUT_MS` 调整；不要用过短固定等待把仍在加载的成功提交误报为“表单未关闭”。测试已经发生主要填写、保存或回读异常时，`finally` 中的弹窗关闭失败只记录为次要清理信息，不得覆盖原始异常和清理前失败截图；没有主要异常时，关闭失败仍须使当前用例失败。

保存按钮命令用例捕获到成功响应后也必须等待原新增表单实例真正隐藏，并等待全局加载遮罩消失，再开始列表、详情或编辑回读。底层列表已经有数据不代表保存后的新记录已经完成刷新；禁止在保存按钮仍处于 loading、弹窗仍覆盖页面时穿透遮罩扫描底层记录。若关闭后 URL 已进入 `/detail`，等待当前详情的记录标识和页面级“编辑”按钮加载，直接执行详情与编辑双回读，不再回到底层列表定位记录。

不要自动删除既有业务记录。同一进程刚完成 Add 并返回业务 ID 的 `ModuleSmokeResult` 可作为本次创建证明；跨运行复用则只能接受当前 `page_scope` 台账中已登记、且能按业务 ID 或至少两个稳定展示值唯一关联到当前列表行的记录。页面上未登记的 `AUTO_`/`UI自动化` 文案加业务 ID 也不得自行升级为 ownership。没有这种安全候选，或候选当前没有可用删除操作时，才新增带唯一标识的记录。普通业务记录、跨页面台账记录、只有自动化文案的记录，以及归属或 ID 不唯一的记录都不得成为删除候选。确认删除前必须按该业务 ID 重新定位并锁定目标行，再校验删除请求 ID 与候选一致；删除响应成功且该记录已证实消失后才移除当前 scope 台账项，取消或失败必须保留。回归覆盖必须分别证明同进程 Add 结果可用于本轮删除、同 scope 登记记录可跨运行复用、未登记 `AUTO_ + ID` 和跨 scope 记录被拒绝、隐藏 ID 时至少两个展示值唯一关联、不可删候选新增回退及无候选时新增回退。
- 删除接口成功后，列表记录消失校验必须重新按业务 ID 或自动化唯一标识查询当前表格；不要对删除前取得的 `rows.nth(index)` / `.first` 行 locator 等待隐藏，因为 Vue 表格刷新、分页或行重排后该 locator 会动态指向另一条仍可见记录，导致把历史记录误判成本次删除未生效。子记录 ID 不渲染到 DOM 时，优先读取删除响应之后、与删除端点同资源族的最新成功 JSON 列表响应，按本次业务 ID 判断记录是否消失；列表记录集合既可能在 `records`/`rows`/`list`，也可能直接位于 `data`、`result` 或 `results` 的数组中。若列表和 DOM 均无法给出 ID 级终态证据，从删除请求的精确业务 ID 调用同资源只读 `detail/{id}`：仅 HTTP 404 或后端明确“不存在”可证明已删除，成功响应中仍有相同 ID 则删除失败。不得因为另一条历史记录具有相同日期、类型等非唯一显示值就判定删除失败；详情查询不可用或响应身份不完整时报告“删除证据不足”，不得写成“记录仍可见”。接口仍返回该 ID 时不得用 DOM 暂时不可见放行。
- 自动化记录台账以 `schema_version`、`page_scope::business_id` 的 `registry_key`、业务 ID、当前运行标识和序号保存归属证明。清理或删除候选只接受当前 `EI_AUTOMATION_RUN_ID` 的同 scope 记录，或本进程刚创建并持有内存证明的记录；历史运行、仅名称带 `AUTO_` 的记录和 scope 不一致记录都不得复用。显示标记只作辅助关联，不得替代该键。
- 删除通用用例按预期分为两类独立闭环：确认类先新增并精确定位 `AUTO_` 记录，再确认删除接口成功及该记录消失；取消类同样先定位自有记录、打开确认框并取消，再重新按业务 ID 或标记确认记录仍存在。关联/流程等页面专属的“不能删除”条件不能由通用框架伪造，通用用例只验证确认框可安全取消，专项用例另行构造该业务前置条件。

## 验证

## 字段身份与动态联动
- 动态明细集合必须通过前端 `data-ei-collection-*` 契约暴露业务字段码、数组路径、模式（`add-row` 或 `selection`）、最少行数和子字段码。执行器先按契约点击真实选择控件或新增入口建立一项，再重新扫描且只填写该项子字段；回读使用 `items.0.description` 等数组路径，不把集合外层字段码当作详情 API 字段。契约缺少新增入口、数组路径或子字段时，明确报告“动态字段契约缺失”，不得继续保存或误报为删除失败。
- 表单命令和对话框标题等自动化内部条目使用 `__` 前缀字段码。写入并重新加载通用字段 manifest 时必须保留其原始 `field_type`，不得按 `kind=text` 归类成业务文本框；绑定时内部条目只匹配工作簿中同类型的显式控件规则，且不得参与必填基线填写或文本/文本域兼容扩展。否则“对话框名称”会被 `ADD-*` 文本用例误填并在保存前制造自动化失败。
- “清空非必填项”命令用例建立合法保存基线时，只上传当前表单的必填附件；完成度检查只忽略尚未填入的非必填附件，必填附件仍必须上传成功。清空阶段必须把已填非必填附件纳入范围：仅在该附件所属表单项内逐个点击真实删除入口并处理确认框，确认控件不再有文件值后保存；Element Plus 自定义文件上传的 `.el-icon--close` 也是删除入口，不能仅识别垃圾桶图标。该关闭按钮可能在文件行悬停前由框架设为 `display:none`，因此先定位可见文件行并悬停，再在该行内重新查找不带 `:visible` 过滤的关闭按钮；多个文件时每次删除后重新读取同一表单项内的文件行和删除入口，确认附件名或行数确实减少，避免使用已失效的 DOM 定位。详情和重新打开的编辑页均要把该附件按空值回读。无删除入口、删除未生效或任一回读仍有文件均为失败，不能跳过或改写必填附件。
- 专项附件持久化用例可显式传入空的普通字段回读集合，表示字段断言已委托给附件校验；该空集合必须跨执行器、保存验证包装层和双回读驱动原样传递，禁止用 `required_codes or submitted` 或真假判断把它恢复为普通提交字段。通用驱动仍须定位同一记录，并将列表即详情的当前承载页或其详情入口用于进入重新打开且就绪的编辑表单，随后由专项用例按唯一附件名断言回显。`required_codes=None` 仍表示普通提交字段回读，不能因表单中没有可比较字段而放行。
- `verify_saved_record()` 入口必须统一规范化回读字段：未映射到源码稳定字段码的 `el-id-*` 及含生成 ID 的嵌套路径不得进入列表、详情或编辑回读；已由运行时身份解析映射成稳定源码字段码的字段正常保留。继续区分 `required_codes=None` 的默认回读与显式 `set()` 的专项委托语义，过滤生成 ID 后得到空集合时也不得恢复成全部提交字段。
- “中英文及常用标点”“HTML/脚本字符”等字符内容兼容性规则同时绑定可编辑的单行 `text` 和多行 `textarea`；同一规则命中的全部文本字段合并为一个表单事务，一次填完并只保存一次，不得因预期文字含“拒绝”就按字段拆成多个对话框。不同规则会给同一字段写入不同值，必须分别使用独立事务。长度边界继续按控件类型、实际 `maxlength` 和布局分别绑定，换行/缩进规则仍仅适用于 `textarea`。覆盖报告必须列出每个实际绑定字段，不能因 Excel 控件名写作“文本”就只执行第一个单行输入框。
- 字段类型只决定候选用例族，不自动证明数值边界。整数专用的“小数输入整数框”仅在运行时/源码明确给出 `precision=0`、`step=1` 等稳定整数约束时绑定；`precision` 缺失不得猜成整数。百分比/比例语义也不得自动补 `0..100` 或两位小数，最小值、最大值和越界用例只绑定 DOM 或源码实际暴露的约束；明确 `max=100` 的控件仍正常执行。
- 数值字段的 `max_digits` 只统计数字，不包含小数点：存在 `precision` 时，边界值的整数位数为 `max_digits - precision`，超限值在该字段自己的 `max_digits` 上增加一位。禁止把小数点扣成一位数字，也禁止用某个金额字段的位数覆盖其他字段已经采集到的约束；回归必须同时证明边界值和多一位值。
- “HTML/脚本字符”的预期是安全处理，不是无条件保存成功：通过路径只能是保存后按文本安全回显，或页面/接口给出明确的脚本、安全策略拒绝。若危险内容请求出现连接重置，只能在同一表单把所有危险值替换为无害等价文本并成功完成一次保存与回读后，判定为内容级安全拒绝；普通超时、网络失败、系统异常或无害探测也失败时仍按真实失败报告，禁止把所有 `ERR_CONNECTION_RESET` 放行。拒绝路径的报告证据必须写明危险内容被拒绝及无害探测记录已保留，不得把原危险输入标成 `persisted`。
- 动态表格内的输入控件常只有“请输入”等占位符，业务标签位于列头。先用同一原生表格的 `cellIndex` 关联 `thead th`；Element Plus 将表头与表体拆成不同 `<table>` 时，再用单元格和表头共享的稳定列 class（例如 `*_column_<n>`）在同一 `.el-table` 根内关联。取得列名后再判断文本、数字或选择控件，禁止按占位符生成通用文本。
- 表头词只补充字段语义，不能覆盖真实控件类型。金额列中的币种 `select/combobox` 仍按选择控件处理，金额输入才按数字处理；“操作、序号”等非业务列不得成为字段标签。
- 控件类型判断必须先看运行时组件语义，再看字段标签启发式：原生 `select`、`role=combobox`、Element Plus/Ant Design select 容器必须归类为选择控件，即使所在表头包含“金额、出资额、数量”等数字词。`readonly role=combobox` 是常见下拉内部输入，不得调用文本 `fill()`。
- Element Plus/Purvar 选择组件不能只扫描内部原生 `input`。下拉、单选框和复选框的真实可见控件可能位于 `.el-select`、`.el-radio-group`、`.el-radio`、`.el-checkbox-group` 或 `.el-checkbox` 组件根，内部 input 可能隐藏或 0 尺寸；DOM 字段发现必须采集这些可见组件根，并用稳定的 `prop`、`field-code` 或 `data-field-code` 生成 selector。否则公共用例会把已渲染的单选框/单选下拉误判为 `not_applicable`。
- Element Plus/Purvar 选择组件的业务标签可能不在原生 `placeholder` 属性上：下拉提示常在 `.el-select__placeholder`，单选组标签常由 `aria-labelledby` 指向独立字段标题。DOM 扫描必须先读稳定标题、`aria-labelledby` 和组件内 placeholder，再把生成的 `el-id-*` 与源码标签匹配；不得把 radio/checkbox 选项文字如“是、否”当字段标签。radio selector 若指向 `.el-radio-group`，执行层必须下钻到组内真实 `input[type=radio]` 或 `[role=radio]` 后再 `check()`。
- 条件渲染的 generated radio/checkbox 若扫描标签只有“是/否/是否”等选项文字，不得按源码位置回填业务身份。仅当源码字段中存在唯一一个明确布尔或状态语义候选时，才可同时映射业务字段码和业务标签，并继续用稳定 `prop` 或业务标签容器定位真实选项；候选不唯一时保留运行时 generated 身份并报告字段身份不确定，避免把后续文本域或其他单选错绑。字段完成度自检必须在普通可见性判断前读取隐藏原生 radio/checkbox 的 checked 状态，已成功交互返回的选择语义值也可作为完成证据。
- Element Plus `el-date-picker type="year"` 的内部输入同样带 `readonly role=combobox`，但它不是普通下拉。运行时扫描必须先根据 `.el-date-editor--year` 归类为 `year`，再应用通用 combobox 规则；交互时在当前可见 `.el-year-table` 中按目标四位年份点击可用单元格，并以输入框最终回写值作为成功证据。仅打开年度面板、看到当前年份高亮，或查不到 `[role=option]` 都不能报告已选择或“没有可选业务数据”。公共用例将该控件绑定到年份规则而非单选下拉规则；必填清空通过日期组件自身清除动作完成并验证值确实为空。
- 普通文本输入缺少 `type=number` 或 `inputmode` 时，结合标签中的稳定数值语义识别数值控件，包括金额、数量、比例、回报率，以及带“年/月/天”单位的周期或期限。单位和括号只用于补充组件语义；选择框仍优先保持选择类型。识别为数值后首次填值即使用数值生成器，不要等保存校验再把通用文本改成数字。
- DOM 扫描按业务字段容器和组件根节点去重。同一个 select/number 组件暴露多个内部 `input` 时只生成一个 `DomField`；交互执行前再次检查真实元素的 tag、role、class 和可编辑性。发现选择器语义时转入选择流程，发现真正只读且非选择控件时立即失败，不得等待 Playwright 的默认 30 秒填写超时。
- 下拉框的 placeholder 只表示提示语，不得作为“已有值”证据。已有值检查只接受真实 selected-item、已选标签、checked 状态或排除 placeholder 后的组件文本；否则企查查、远程搜索等必填控件会被错误跳过，并在保存时只留下泛化“请输入”校验。
- 运行时组件路径可能使用 `/srcEi/views/`、`/src/views/`、`src/views/` 或 `@/` 别名。源码字段发现必须保留 `srcEi`/`src` 来源族，再解析页面的弹窗组件；不得因路径别名不一致退化为动态 `el-id-*` 字段，否则保存成功但响应不返回主键时会失去名称回查依据。
- 页面同时存在 `localComponent` 和后续无关 `componentPath` 时，优先解析目标 CRUD 的 `localComponent`。例如 `localComponent: "Modify"` 应相对当前 `index.vue` 目录解析为 `Modify.vue`（或 `Modify/index.vue`），并继续使用当前页面的 `srcEi`/`src` 来源族；禁止取后面的跟进、查看等 `componentPath` 作为新增表单。
- 页面入口自身没有字段契约但显式渲染唯一一个相对 import 的本地字段组件（例如详情内联编辑的 `<Modify />`）时，源码字段发现必须跟进该组件并提取其 `PurvarCol`/`el-form-item` 字段；若同页存在多个含字段本地组件，保持未解析，不按源码顺序猜测。
- 源码字段发现遇到只渲染一个本地组件的透明入口时，沿该组件继续解析；其后 `componentPath` 可以是直接字符串或同文件唯一静态字符串 `const`。只采用唯一的字段表单候选；多个被引用组件都含字段时保持未解析，禁止按目录顺序猜表单。
- 模板用静态 `v-for` 字段配置数组渲染一组输入控件时，源码发现应把可确定的 `fieldCode + label` 对逐项展开为稳定字段定义，并排除 `field.fieldCode` 一类循环变量占位符，禁止把它追加成第三个伪字段；运行时绑定继续按业务字段码优先、标签次之，不得把整个循环控件当成一个字段或按 DOM 下标对齐。
- 顶层操作与对话框嵌套操作保留独立的采集身份和断言结果，但同一页面、同一外层操作下选中的全部 `operation_path` 必须合并到一次父表单生命周期中执行。完成全部嵌套行新增、删除或其他动作后，只填充和保存一次父表单，再完成保存响应、业务主键及详情/编辑回读闭环。禁止仅因嵌套按钮已点击或行数已变化就报告通过，也禁止为每个嵌套节点重新点击外层入口、创建重复业务数据。
- 嵌套表格新增不能以“按钮已点击”作为通过标准。点击前后统计目标 section 内的业务表格行数，等待响应式渲染后必须增加至少一行；定位时滚动目标 section 到视口并保留可观察停留时间。行数未变化时失败，不得打开父新增弹窗后直接报告通过。

- 点击新增后，先等待对话框或内嵌表单外壳出现，再等待其可见加载遮罩消失且至少一个可编辑控件出现，然后才能扫描和填写字段。禁止用固定毫秒等待代替表单就绪判断；超时应报告“表单控件未加载完成”，不得把尚未渲染误报为全部源码字段未定位。
- 打开详情编辑或保存后重新打开编辑表单时，在点击编辑入口之前注册短生命周期的 XHR/fetch 响应监听，并保留到该表单完成就绪判断。若详情类接口返回 HTTP 失败或 HTTP 200 业务失败，必须优先报告其请求方法、无查询参数的 URL path、HTTP 状态和有限错误信封摘要，不得继续误报“表单控件未加载完成”；监听在成功、失败、页面重绑定时都要移除。诊断不得包含 query、请求体、响应业务数据、凭据或 Cookie，响应摘要只允许白名单错误字段并对 token/password 等值脱敏。
- 以表单项的业务属性（例如 `prop`、`name`、`data-field-code`）作为字段身份；Element Plus 的 `el-id-*` 仅可作为本次渲染的临时定位器，禁止用作字段代码、语义判断或源码字段匹配键。
- DOM 字段与源码字段必须优先按业务字段代码匹配，禁止仅按数组下标对齐。动态显示、条件隐藏和重复包装控件都会改变 DOM 顺序。
- Vue 组件上的 `el-form-item prop` 不保证渲染为 HTML `prop` 属性。运行时取不到业务码时，从 `PurvarCol` 等最小字段容器提取可见标签，规范化星号、空白和中英文冒号后与源码标签匹配；字段码、标签都无法匹配时才允许位置兜底。
- Purvar 表单把业务标签和控件渲染在 `.purvar_form_item` 的同级列时，标签提取优先读取不包含当前控件的首个直接列，再读取独立 label/title 节点；禁止从 `.purvar-col__content` 或选择组件当前值提取字段标签。radio/checkbox 的扫描 owner 优先使用最近的 group，同组内部组件和隐藏 input 只能生成一个业务字段。
- `prop` 常位于表单容器而不是可交互元素。填值前把定位结果收敛到容器内实际可见的 `input`、`textarea`、`select` 或 ARIA 控件；选择框和单选框按业务字段定位整个控件组。
- Element Plus 或业务自定义选择器可能不把最终值写入原生 `input.value`。普通文本仍必须读取 DOM 实值；选择类控件可用“标准 selected-item/checked 状态”或“候选项点击并完成确认且交互返回语义值”作为已输入证据。交互返回的非空语义值写入 `submitted` 后，字段完成度检查和重试规划必须把该字段视为已填，不能因内部搜索输入仍为空而重复选择或报告未填写；自定义字段声明为文本但运行时节点是 `select`/`role=combobox` 时转入选择流程，并优先点击所属组件的可见 wrapper。弹窗表格、树和组织选择器必须完成确认动作，不能只点击候选行。
- Element Plus select 可能同时渲染多个 `.el-select__selected-item`：第一个是空输入包装层，后续节点才包含“人民币/欧元”等真实选中值。已有值检测必须遍历全部候选节点，并保留 wrapper 显示文本兜底；任一非透明节点具有非空文字或 value 就视为已填，禁止命中空包装层后误判为空并改写原值。
- 单选框不得因字段身份是否解析成功而选择 DOM 中的 `first`/`last`。先用稳定字段代码或规范化标签锁定整组，再按覆盖、采集或配置给出的明确业务语义值匹配选项文字/value；已有 checked 值时保持不变。`isRegister` 等字段识别失败只能形成定位诊断，不能因此把“未注册”切换成“已注册”或改变任何业务选择。
- 模块级 `choiceValues` 是经过验证的显式合法分支契约，优先级高于页面默认 checked/selected 值；它只能在精确 `formCode` 和稳定字段码或唯一标签别名命中时生效，并按选项文字/value 精确选择。普通未声明字段仍保持已有值，probe 仍不得读取页面专属基线；显式切换后必须重新扫描条件字段和动态集合。
- 单选/复选的已有值自检必须使用解析后的稳定业务字段码和业务标签作为兜底。当前 `el-id-*` selector 缺失、过期或命中隐藏内部节点时，先在当前表单内按 `field-code`、`data-field-code`、`prop` 或规范化字段标签锁定字段容器，再读取 `input:checked`、`aria-checked=true` 或 `.is-checked`；已存在 checked 证据时跳过填写，不得继续对 generated ID 执行 `check()`。
- 一个业务字段由金额、币种、单位等多个子控件组成时，`submitted` 中保留首次取得的主业务值；后续子控件显示文字只能作为辅助信息，禁止覆盖主值后导致详情比较失真。
- 每次选择或单选导致条件字段切换后重新扫描 DOM，不复用旧 ID 或旧 Locator。源码中的条件组件只说明可能能力，当前运行时 DOM 才决定此刻应按普通输入框、下拉框还是远程搜索控件交互。
- 对联动字段选择可完成闭环的合法路径。若某组选项会切换到依赖外部数据的远程控件，而另一合法选项会产生普通可填写控件，probe 模式可优先选择后者；不得在远程控件无候选时把“已定位但无可用数据”误报为“字段未定位”。

修改上述行为后，至少覆盖以下回归：动态 ID 不成为业务代码、源码与 DOM 顺序不同仍按代码匹配、容器定位可落到真实输入控件、联动重渲染后使用新控件。

修改动态表格字段识别后，回归还必须覆盖：同表 `cellIndex` 表头关联、Element Plus 分离表头/表体的列 class 关联、数字输入生成数值、同一金额列的币种下拉仍保持选择类型，以及“操作/序号”列不产生业务字段。

保存后表单没有消失时，先检查已捕获保存响应的 HTTP 和业务状态，再汇总所有可见 `.el-form-item__error`、Element Plus message 和 `[role=alert]`。不要只报告“表单未关闭”。浏览器失败附件遵循 `ui-smoke-test`：只附当前 URL 和一张截图；执行器会清理弹窗或下拉时先捕获当前视口现场，没有现场缓存时才回退全页截图。不得包含凭证、Cookie 或 storage state。

编辑保存接口常以 `/update`、`/edit` 或 `/modify` 命名，而非 `/save`。保存响应监听必须把这些有提交字段重叠的 POST/PUT/PATCH 响应纳入业务候选并排除附件请求。点击保存后，先在等待窗口内持续采集新出现的字段校验错误和页面 warning/error；若阻断保存，报告具体提示。Excel 的“输入框、选择框、取消/关闭按钮”应分别映射到标准 text、select、cancel 控件；“清空非必填项”保存场景未实现清空及保存后回读时标记不适用，禁止按普通保存通过或失败。



提交前固定本次表单的原始 DOM 元素句柄，保存后的关闭等待和最终断言只检查该元素。禁止继续使用 `[role="dialog"]:visible`、`.el-dialog:visible`、`.el-drawer:visible` 等动态 Locator 判断原表单是否关闭；原弹窗消失后 Locator 会重新解析并可能命中新出现的消息框、详情层或其他可见容器，从而把“保存成功、弹窗已关闭、列表已回显”误报为“表单未关闭”。原元素 detached/hidden 视为已关闭；原元素仍可见时才读取其校验错误并失败。修改此逻辑时必须回归覆盖：原元素已关闭但动态 Locator 仍命中其他容器，以及原元素确实仍显示两种情况。
- 保存后的 Vue 重渲染可能先使固定表单 Locator 无法解析，随后原元素句柄才更新为 hidden/detached。错误采集发现固定 Locator 已不可见、无法解析或扫描异常时，必须停止读取旧表单字段，立即降级为仅收集页面级错误消息并继续保存响应分类；不得让失效 Locator 的默认等待覆盖已发生的业务结果。

## 保存响应与结果分层

- 先独立判断 HTTP 与业务状态，再提取业务主键。响应 `data` 为空不代表保存失败；主键可能位于顶层或常见响应信封中。
- 响应含非空 `errors` 时，即使旧接口同时返回 `status='1'` 等成功样式，也按业务失败处理。HTTP 非 2xx 时保留有限长度、脱敏后的响应摘要用于诊断，但不根据 `SYSTEM_ERROR`、系统异常或模糊 500 文本自动生成字段值。
- 保存接口业务成功但新增响应未返回主记录 ID 时，报告“保存成功后的自动化校验失败”，不得按名称或列表顺序猜测记录。仅对已从当前详情页打开、且调用方显式提供既有业务 ID 的编辑保存，响应可不重复返回主键；该 ID 仍必须用于精确详情回读。任何详情字段证据缺失都失败，禁止只按“操作成功”通过。
- 新模块返回未知主键键名时，先用真实成功响应确认语义，再把键名加入 `verification.py` 的集中主键集合并添加与真实响应形状一致的单元测试。禁止只在模块驱动中写页面专属分支。
- 保存接口已经返回业务成功时，后续主键提取、列表定位或详情验证失败应报告为“保存成功后的自动化校验失败”，不得描述成业务新增失败。日志应保留业务状态、脱敏后的响应形状和失败阶段。
- 主键提取成功只表示可以继续验证，不等于新增闭环通过；仍需完成列表或详情回显核对。

## 根因沉淀规则

每次完成“诊断 -> 修改 -> 重跑通过”后，先写一句可证伪的根因，再决定是否更新 Skill：

- 写入对应 Skill：根因属于公共框架、公共组件、通用测试驱动、重复工作流或稳定接口契约，并已有真实运行证据和回归测试。
- 不写入 Skill：仅是某条测试数据不可用、临时网络/权限问题、单页一次性 selector、未证实推测或已有规则的重复表述。
- 更新位置：新增冒烟和字段交互写入本 Skill；模块发现写入 `runtime-module-discovery`；数据生成写入 `smoke-test-data-strategy`；总执行和 Allure 编排写入 `ui-smoke-test`。
- 写法要求：记录可复用的判断条件、处理顺序和验证标准，不记录本轮流水账、动态 `el-id`、具体测试数据或敏感环境信息。
- 完成标准：Skill 更新与代码修复在同一轮完成，运行对应定向测试和真实模块复测；若判断无需写入，也在最终结果中简述原因。

## 非标准 CRUD 闭环

- 仅当模块能力配置明确要求新增时设置 `EI_REQUIRE_ADD=true` 并进入 CRUD 闭环。设置页、行内配置页即使存在“新增”文本按钮，也只执行页面访问检查，禁止仅凭按钮文字猜测能力。
- 编辑、立项准备、入库申请等打开可编辑业务弹窗的操作不能以“弹窗已打开”通过。扫描并补齐当前弹窗字段，等待附件完成，再点击底部提交命令并校验真实业务保存响应。提交按钮不一定叫“保存/确定”；优先匹配弹窗 footer 中与当前业务操作同名的精确命令（如“立项准备”），再回退到保存/确定，禁止点击表单内容区的同名按钮。
- 非标准弹窗保存复用与普通 CRUD 相同的持久化闭环：保存响应中的主键优先；响应未重复返回主键时只接受调用方从当前记录上下文显式传入的既有业务 ID。随后必须用该 ID 调共享详情 helper 核对稳定提交字段，返回 `dialog_action_detail_verified`；不得返回仅表示保存响应成功的结果，也不得按名称寻找记录。
- 内联详情编辑中，`.el-form` 可以只承载字段，保存、提交和取消按钮则作为 `.detail-panel` 或 `.base-info-page` 内的相邻工具栏。命令发现和执行先限定在表单；表单内没有命令时，仅向上扩展到最近的上述页面容器，确认其中存在表单命令后再操作，禁止放宽到整个页面。取消后原表单未隐藏时，只有同时不存在可编辑控件和表单命令按钮才可判定已退出编辑态；仍须确认没有业务保存请求。
- 页面自身没有表单契约而通过本地 `*Form.vue` 子组件承载表单时，跟随实际 import 提取子组件的 `el-form-item prop`、标签和控件；禁止把动态 `el-id-*` 当业务字段代码。
- 源码中存在但当前 DOM 因条件分支、只读状态或联动选择而未渲染的字段写入 `expectedNotRendered`，作为信息而非保存阻断条件。当前可见可编辑控件的空值和交互异常才进入阻断判断。
- 保存后点击编辑若不产生详情 XHR，允许用重新打开的编辑表单逐字段核对本次提交值。至少存在一个可比较字段且全部一致时，结果记为 `add_and_edit_form_verified`；不能仅因没有详情接口直接放行。
- 新增类页面操作的最终断言同时接受 `add_and_detail_verified` 和 `add_and_edit_form_verified`，因为二者都完成保存后数据核对；不得接受 `page_access`。运行时组件未匹配所选源码时必须启动前失败，不能以 `supports_add=False` 降级成页面访问假成功。
- 树型 CRUD 用业务名称定位新节点并点击触发详情；树候选必须排除自身或祖先为 disabled 的节点。存在 `data-key` 时记录真实业务键，不以节点显示文本代替提交值。
- 可选 `parentId`、`relationId` 等关系字段没有明确测试数据时保持空值，写入 `optionalNotFilled`/`optionalFillFailed`，但不阻断保存；必填未输入和必填交互失败仍必须阻断。
- 无字段名的“实体已存在”提示只有在表单中恰好存在一个远程企业字段时才允许修复。每轮使用不同搜索词选择新的真实候选，受保存重试上限约束；禁止伪造选择器值。远程企业控件优先根据当前 `el-select` 的 `aria-controls` 绑定其拥有的可见下拉层，并读取标准 `.el-select-dropdown__item`；仅在该控件没有拥有的下拉层时兼容旧版表格或树候选，不能假定 QccSelect 一定渲染为表格行。
- 远程企业控件修复后，使用 Qcc 页面冒烟验证“打开新增、输入关键字、选择一个真实候选”，但不点击保存。部署模块可通过 `EI_FORM_URL`、`EI_QCC_ADD_BUTTON` 和 `EI_QCC_FIELD_LABEL` 提供实际页面、可见新增按钮和企业字段标签；检查应断言搜索请求已发出、返回存在候选且控件实际完成选择。再用无部署依赖的驱动契约覆盖“拥有的 popper 返回标准 Element Plus 选项”路径，防止后续改动重新退化为只扫描表格或树。
- 首轮填写全部目标字段；后续字段填写轮次只重跑当前 DOM 仍为空或上一轮交互异常的业务字段，禁止重新点击、覆盖已成功字段。每轮用最新结果替换旧失败，不能累加已经修复的历史异常。保存校验修复仍只处理提示唯一映射到的字段。
- 新增或编辑表单首次扫描时也先读取实际值：文本、日期、已选单选/复选、标准 selected item 及 Element Plus 非透明选中占位均视为已有值，禁止重新生成、点击或切换。只有字段为空时才执行普通填写；仅当该字段出现可唯一映射的校验错误时，才允许修复已有但非法的值。“已有值不修改”只约束交互，不能丢弃预填的名称、全称或标题；在最终填写和修复完成后从当前父表单读取这些非敏感稳定值，作为独立于 `submitted` 的记录定位标识。保存后列表不展示业务 ID 时用该标识定位回读，嵌套表格行值和动态 `el-id-*` 不得成为外层记录标识。
- 附件遵守相同的“已有值不修改”规则。每次默认上传前检查 `input.files` 和所属表单项内已完成的 Element Plus/Ant Design 附件列表；只有 `input.files.length > 0` 或当前附件表单项存在明确的 `is-success`/`done` 状态才算已有附件，单独出现文件名节点、上传列表外壳或占位节点均不能作为已有值证据。页面原有附件或前一轮已上传成功时必须跳过。字段重试轮次不得无条件重复上传，但后续新渲染且为空的文件控件仍应上传。保存前字段完成度自检必须复用同一附件证据，并在普通可见性门槛之前检查隐藏的原生文件输入；禁止出现上传报告为 `existing`、完成度报告却把同一附件判空的矛盾结果。
- 附件上传是异步前置步骤，不得用固定休眠后立即点击业务保存。监听本轮上传请求及完成/失败事件，等待所有上传请求结束并稳定空闲，同时核对 Element Plus/Ant Design 上传列表不再处于 `uploading/progress` 且出现成功状态；任一失败状态或超时必须阻断保存。多个文件输入可能共享同一表单区域，禁止用前一个文件的成功标记判定后续文件已完成。附件“上传成功”提示和附件接口响应不能作为主业务保存成功证据，仍须捕获包含已提交业务字段的真实保存请求。
- 已能从文件输入值或组件成功态证明上传完成时，不得因本轮尚未捕获到上传网络请求而误判失败；网络事件用于等待和诊断，不能覆盖已确认的 UI 完成证据。

## 字段诊断产物

- 每个模块写入独立 JSON，并更新 `latest.json`。至少记录模块、路由、组件、轮次、最终状态、源码预期字段、运行时实际字段、已提交字段代码和校验修复历史；不要写入字段实际敏感值、凭证或完整请求体。
- Keep a regression for empty locked-form scans: the diagnostic omits control values, and the raw-control fallback remains conditional on a supplied form root rather than page-wide discovery.
- A generated Element Plus ID, including its numeric suffix, is never a cross-render field identity. Rebind only through a stable business code, unique normalized label plus compatible control kind, and the current form/section path; ambiguous candidates must fail with a field-identity adaptation error rather than selecting the first control.
- 当已锁定表单作用域仍有可编辑控件、但 DOM 字段扫描结果为空时，诊断必须同时记录控件标签、输入类型、动态 ID、`name`、最近表单项 `prop`、几何尺寸、CSS `display/visibility`、隐藏祖先类型和只读状态，且不得读取控件值。先用该证据区分容器错选与扫描过滤缺陷，再修改定位逻辑；不可把它误报成字段尚未水合。Element Plus 外层弹窗可能保留陈旧 `aria-hidden=true`，对已锁定且几何可见的表单根节点只可忽略“包含该根节点”的祖先标记；根节点自身及内部真实隐藏子区块必须继续过滤。
- 当已锁定表单作用域仍有可编辑控件、但 DOM 字段扫描结果为空时，诊断必须同时记录控件标签、输入类型、动态 ID、`name`、最近表单项 `prop`、几何尺寸、CSS `display/visibility`、隐藏祖先类型和只读状态，且不得读取控件值。先用该证据区分容器错选与扫描过滤缺陷，再修改定位逻辑；不可把它误报成字段尚未水合。Element Plus 外层弹窗可能保留陈旧 `aria-hidden=true`，对已锁定且几何可见的表单根节点只可忽略“包含该根节点”的祖先标记；根节点自身及内部真实隐藏子区块必须继续过滤。若该锁定根的可见性扫描仍为零，才可在同一根内回退到原始控件集合；页面级扫描不得回退，且后续仍按标签/业务码验证身份，禁止按顺序输入。
- 判断“最新一次执行”时交叉核对 `moduleId`、运行时组件、pytest node、执行时长和诊断时间戳，不能只打开文件名相近的旧模块日志或旧 Allure 结果。若进程仅运行数毫秒且没有产生更新的字段诊断，应判定实际只走了 `page_access` 或启动前分支，不能当作 CRUD 已执行；结论中明确区分最新运行产物与历史产物。
- `notLocated`、`notFilled`、`fillFailed` 表示阻断闭环的问题；`optionalNotFilled`、`optionalFillFailed` 和 `expectedNotRendered` 只提供事实信息。禁止为了让状态通过而把必填失败降级到可选分组。
- `actualFields` 保留字段代码、标签、控件类型、必填、只读和是否有值。动态 DOM ID 只用于本次运行定位，不能作为跨轮修复键。

## 对话框嵌套新增

- 对话框内部存在独立表格或表单区块时，不把所有同名“新增”当成页面入口。执行目标必须携带完整操作链，例如 `新增 -> 股权结构 -> 新增`。
- 按顺序执行操作链：先点击页面外层新增并等待 Dialog/Drawer/内嵌表单就绪，再按精确区块标题定位当前表单作用域内最近的、包含命令按钮的祖先区域，最后点击该区域内的目标按钮。
- 先填写父表单中会控制分区显示或清空分区值的联动字段，等待父表单联动稳定后，再触发嵌套新增并扫描动态行字段。禁止先填嵌套行、再切换投资类型/注册状态/所在地等父字段；后续联动可能清空已填子表数组。嵌套新增后重新扫描字段，不复用点击前的 Locator。
- 嵌套新增后以新建表格行为独立 DOM 作用域立即扫描和填充，使用该行的表头/字段容器语义识别控件，不得继续只扫描父对话框字段。文本、单选、下拉、组织联动等所有交互帮助方法都必须接收并限定到该行作用域，禁止扫描在行内、点击却回到页面全局命中父表单同名控件。新增行没有可编辑控件、必填控件仍为空，或没有形成带分区身份的提交字段证据时必须失败；父表单保存成功不能覆盖这些失败。
- Element Plus 固定列可能复制 `.el-table__row` 和输入控件；行数变化、动态行填充和行内删除优先限定到主 `.el-table__body-wrapper`，不得把固定列克隆行计为新业务行或在克隆输入框中制造仅界面可见、未进入 Vue 提交模型的值。
- 对话框操作链中的新增仍属于真实 CRUD。启动器必须传递操作链并启用新增闭环，不能只做按钮可见性检查，也不能退化成外层普通新增。
- 嵌套行填写完成后继续提交外层业务表单，并沿用保存响应、业务状态、主键和详情/编辑回读校验。子区块按钮点击成功本身不代表测试通过。
- 回归用例至少覆盖：同一对话框两个区块均有“新增”、按标题限制按钮作用域、操作链序列化传递，以及动态行出现后才开始字段扫描。

## 对话框嵌套操作

- 同一页面、同一外层操作下选择多个嵌套操作时，按 UI 顺序聚合完整 `operation_path`。外层新增/编辑对话框只打开一次，在同一父表单内依次执行全部嵌套操作，最后统一保存并回读一次；即使只选择嵌套节点，也应合成一次对应的外层操作执行。
- 嵌套分区不限于新增。按 `operation_path` 的末级动作分类执行：新增/添加/新建必须使目标分区行数增加；删除/移除/清空在空白父表单的目标分区创建足够的自动化临时行，只删除明确定位的目标行并在确认框中确认，随后验证行数减少，同时保留满足父表单校验所需的有效行。其他命令必须观察到新弹窗、路由变化或 XHR/Fetch。完成分区动作后必须继续填写并保存父表单，捕获成功响应、取得主键并完成详情或编辑回读；只验证行数变化不得通过。
- 行级删除按钮通常只在表格存在数据行后渲染。破坏性嵌套操作不得在创建临时行之前统一等待目标删除按钮；先定位分区新增入口并创建行，确认行数增加后，再把按钮查找限定到新创建的行内并执行删除。
- 禁止为了验证嵌套删除而选择已有业务行。无法创建并稳定定位临时行时直接失败，不点击任何已有行的删除按钮。
- 同一分区的新增和删除是两个独立采集节点，保留完整的“外层入口 / 分区 / 操作”身份；执行时可在同一次外层对话框中依序完成，但每个节点仍必须满足对应动作的效果断言。

## Common-field case lifecycle

- Treat every workbook case whose expectation mentions saving, blocking, list/detail display, or persisted consistency as a save transaction. Never pass it from control acceptance, normalization, truncation, or character counting alone.
- Edit value-correctness rules apply to every rendered single-line text and textarea target in one compatible transaction. Derive each target value from its current edit value, change only the workbook-requested portion, preserve unrelated populated controls, Save once, and verify every changed field after persistence. A select edit-correctness rule is different from a fixed-option-list assertion: choose an available option different from the current selection, then Save and read it back.
- Bind dialog-title checks only when the active edit form is actually hosted by a visible Dialog/Drawer with a non-empty title; inline edit forms make that row `not_applicable`. Normal edit baselines must preserve populated attachments and must not re-upload them merely to increase coverage. An explicit attachment edit rule such as `EDIT-004` is the exception: add one uniquely named temporary copy of the configured fixture only to its target attachment control. Register attachment lifecycle listeners before `set_input_files` and keep them active through the business Save; wait for OSS upload, file-list/merge, CommFile, and dynamic `tenantForm/saveFormData` or `updateFormData` requests to finish successfully plus a bounded quiet window before reopening the record. The upload row whose displayed file name exactly matches the new fixture must also enter success state. On reopening the same record's edit form, prefer the exact unique-name echo; when the server rewrites file names, accept only a new same-suffix file in that exact target form item relative to its pre-upload file list. A successful older attachment in the same form item, a page-global attachment name, or a new file from another field must never satisfy the assertion. Never delete or overwrite an existing attachment to gain coverage. During save/detail response association, multipart file-upload traffic is an eligible observation but never JSON input: safely treat an exception from Playwright's `request.post_data_json` property as unavailable payload, then fall back to URL and raw `post_data` identity matching. This must not abort verification of later business or detail responses. On Windows, Chromium may briefly keep the temporary upload fixture locked after `set_input_files`; cleanup must use bounded retry and deferred best-effort deletion, and a cleanup-only `WinError 32` must not replace the upload/save/readback result. An upload lifecycle failure, post-save attachment lifecycle failure, save failure, or absent reopened-edit attachment is a test failure, not `not_applicable`.
- An edit form shell and its ordinary controls may become visible before asynchronously hydrated attachment controls. For an explicit attachment edit case, keep the pinned form instance and poll its fresh runtime field scan for the exact attachment identity through a bounded hydration deadline before declaring the field absent; do not broaden the search to another form or fail on the first incomplete scan.
- Treat a runtime file identity shaped as `file:<business label>` as an internal synthetic field key. Retain the full key for field identity and reporting, but strip only the `file:` namespace before matching a rendered detail/list label; still require the associated value within that labeled field and never replace field-level readback with a page-global file-name search.
- For an edit rule that clears non-required values, fill/preserve the legal baseline without uploading optional attachments, clear every populated optional control that exposes a real user clear action, and verify those stable field codes as empty in both detail and reopened edit views. Treat absent, `null`, and empty-string readback as equivalent only when the expected value is explicitly empty and the record is independently associated by business ID or stable automation marker; a non-empty value must still fail.
- When merging source field definitions with runtime DOM fields, never let a source `ElInput-TEXT` downgrade a runtime or stable-field-code numeric semantic to plain `text`; use source metadata only to enrich labels/constraints, while rendered component kind and stable-code semantics decide common-case binding. Regression coverage must include `buildPeriodMonth` as `number` and a non-numeric sibling such as `buildScale` remaining `text`.
- Keep symbolic workbook input specifications executable end to end. When normalization produces a sentinel such as `__REPLACE_LAST_WITH_9__`, rule binding must preserve it as applicable, and the executor must resolve it from the current control value at runtime; do not silently drop the case merely because the sentinel is not a literal form value.
- Percentage semantics must use both label and stable field code. Numeric controls whose stable code ends with `Rate`, `Ratio`, `Percent`, or `Percentage` bind percentage workbook rows, not generic number rows; stale manifests are normalized again at load time so direct validation cannot keep executing old `number` bindings for fields such as `expectedReturnRate`.
